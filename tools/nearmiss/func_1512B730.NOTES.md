## What it is
Per-player (`arg0->unk23D`, 0-3) analogue-stick / input-history evaluator. `D_800DC0C0` is an
array of four 0x4C-byte records; each record is four `struct Struct1512B5FC` (the type
already in this TU, written by `func_1512B5FC`/`func_1512B630`) plus a `u8` direction latch at
+0x30. It latches which of the two axis pairs went active last, then writes a signed delta
into `*arg1` from the per-player threshold table `D_800DC200[unk23D][unk1B4].unk0 + 1`, and
finally runs a `unk3F0` countdown that saves/restores the camera pair (`unk374`,`unk348`) into
(`unk3F4`,`unk3F8`) using -1.0f as the "not saved" marker.

New types introduced: `struct Struct1512B730 { struct Struct1512B5FC unk0[4]; u8 unk30;
u8 pad31[0x1B]; }` (0x4C) over the existing `extern u8 D_800DC0C0[]`.

## The lever that made this function: `u8` kind locals
Caching the four latch bytes as **`u8 k0..k3`** instead of `s32` took the diff from
opcode-diff 36 (238 insns) to opcode-diff 3 (247 insns) in one edit — worth ~10 instructions
and ~130 rows. With `s32` locals IDO CSEs the literal `2` into a t-register once
(`li t5,2` … `bne t1,t5`); with `u8` locals every comparison emits the immediate form, which
the assembler expands to a per-site `li at,2` and which then also becomes the instruction
IDO duplicates into the branch-likely delay slots (`beql t2,at,+4` / `li at,2`). Nine of the
ten missing instructions were those `li at,2`.

> Generalisable: when golden materialises the SAME small constant repeatedly in `$at` and
> your output hoists it into one t-register, narrow the compared variable's declared type.

## Other things that mattered
* Cache the four latch bytes in locals but write the record address as an EXPRESSION
  (`REC` macro) everywhere else. Golden reloads `arg0->unk23D` after every `sb` to the record
  (store through the `D_800DC0C0` base vs load through `arg0` — different pointers, no
  disambiguation) but never reloads the latch bytes (same base `t1`, different offsets —
  disambiguated). Caching the address in a pointer local kills the first behaviour; not
  caching the bytes kills the second.
* `((struct S *)D_800DC0C0)[arg0->unk23D]` (direct subscript) gives golden's base-first
  `addu t1,v0,t6` AND keeps the 0x4C multiply as `multu <idx>,v1` with 0x4C CSE'd into `v1`.
  A byte-offset form (`(u8 *)D + i*0x4C`) expands the multiply into a 5-instruction shift
  chain instead — the opposite of the cookbook's game_13D350 finding, so check both.
* Both arms of `if (arg0->unk23C != 0) … else …` in the "exactly one axis active" branch
  compute the identical expression. That is what golden does; it is an original-game
  redundancy, not a transcription error, and merging them loses 6 instructions.
* `arg2` is a real third parameter that is never read; it is homed (`sw a2,0x8(sp)`) purely
  because IDO reuses `a2` for the 0/1 return flag. No `arg2 = arg2;` idiom is needed.
