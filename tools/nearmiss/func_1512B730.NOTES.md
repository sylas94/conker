## What it is
Per-player (`arg0->unk23D`, 0-3) analogue-stick / input-history evaluator. `D_800DC0C0` is an
array of four 0x4C-byte records; each record is four `struct Struct1512B5FC` (the type
already in this TU, written by `func_1512B5FC`/`func_1512B630`) plus a `u8` direction latch at
+0x30. It latches which of the two axis pairs went active last, then writes a signed delta
into `*arg1` from the per-player threshold table `D_800DC200[unk23D][unk1B4].unk0 + 1`, and
finally runs a `unk3F0` countdown that saves/restores the camera pair (`unk374`,`unk348`) into
(`unk3F4`,`unk3F8`) using -1.0f as the "not saved" marker.

### The law the 720 sweep settles

Exactly **10** of the 720 orderings score 160 and nothing scores lower. They are precisely the
orderings in which **`k0`'s load comes first**; among those, the relative order of everything
else is irrelevant (`k0` first with the rest untouched, `k0,k1` first, `k0,k1,k2,k3` first —
all identical at 160). So the rule is not "this exact permutation", it is *one load has to be
issued before the two float loads*. The remaining 710 orderings spread from 190 to 7000+.

## The lever that made this function (unchanged): `u8` kind locals
Caching the four latch bytes as **`u8 k0..k3`** instead of `s32` took the diff from
opcode-diff 36 (238 insns) to opcode-diff 3 (247 insns) in one edit. With `s32` locals IDO
CSEs the literal `2` into a t-register once; with `u8` locals every comparison emits the
immediate form, which the assembler expands to a per-site `li at,2`.

> Generalisable: when golden materialises the SAME small constant repeatedly in `$at` and
> your output hoists it into one t-register, narrow the compared variable's declared type.

## Other things that mattered
* Cache the four latch bytes in locals but write the record address as an EXPRESSION
  (`REC` macro) everywhere else. Golden reloads `arg0->unk23D` after every `sb` to the record
  but never reloads the latch bytes. Caching the address in a pointer local kills the first
  behaviour; not caching the bytes kills the second.
* `((struct S *)D_800DC0C0)[arg0->unk23D]` (direct subscript) gives golden's base-first
  `addu t1,v0,t6` AND keeps the 0x4C multiply as `multu <idx>,v1`. A byte-offset form
  expands the multiply into a 5-instruction shift chain instead.
* Both arms of `if (arg0->unk23C != 0) … else …` compute the identical expression. That is an
  original-game redundancy, not a transcription error; merging them loses 6 instructions.
* `arg2` is a real third parameter that is never read; it is homed (`sw a2,0x8(sp)`) purely
  because IDO reuses `a2` for the 0/1 return flag. No `arg2 = arg2;` idiom is needed.

## Next move for whoever picks this up

Every straight-line run in the function has now been swept exhaustively and 160 is the floor of
all of them, so the cheap statement-order gradient is spent. What is left is the pair the
sweeps cannot reach:

1. **The missing instruction (100 of the 165).** Golden duplicates the merge block's
   `lh v0,0x3F0(a0)` into the `b`'s delay slot; we sink our own last instruction instead. The

Those two are plausibly one problem, not two: the delay-slot fill choice depends on which
registers are live at the branch, so a register assignment that matches golden may well make
IDO choose the copy by itself. That makes the register webs the thing to attack, and it is now
known that STATEMENT ORDER — not spelling — is what moves them in this function. The
untried axis is the order of statements *across* the branch bodies rather than within them.
